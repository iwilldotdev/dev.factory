# M5 notes: what was decided where the docs left room

M5 delivers the feedback phase after ship, human checks, quality checks (baseline, delta, scoped, guideline rules), the design note and risk rules, `verify --estimate`, and the metrics completion (`--all`, idle time, tokens). Parity rows 7, 23, 31, 37, 38, 39, 42, 64, 74 and 75; lessons L-24, L-60 to L-62, L-176, L-183 and L-189 (plus tests that touch L-20, L-135, L-136 and L-155 again).

Decisions:

- **Phase after ship.** `done` now needs `gate feedback`. After the ship gate the phase is `feedback`, or `build` while a feedback round has findings at the shipped commits and nothing was read back since. A harness that stopped at "done" after the ship gate now stops at `feedback`; the existing tests were changed for that and nothing else.
- **Refresh.** A change or pipeline read again for feedback is tagged `refresh: true` (`fetch` or `ingest --refresh`). `factory feedback` fetches both through the configured adapters by itself (`--no-fetch` reads what was ingested). The ship gate does not compare a refresh-tagged readback with the plan: a reviewer renaming the change, marking it ready or merging it is not a ship mismatch. `gate feedback` still needs it proof-grade (adapter, or `confirm`) and at the shipped head.
- **Findings.** `thread:<id>` is `major`; `job:<pipeline id>/<job name>` is `major`, or `minor` when the job may fail; `pipeline:<id>` covers a failed pipeline with no job detail. The same source at the same commits is never a new finding, so refreshing twice records one round; a new commit makes an unresolved thread a finding again, which spends another loop. A merged change needs no thread fix. There is no "dismiss a finding" command: the thread is resolved at the SCM, a commit changes the heads, or the user waives the pipeline.
- **Loops.** One round with a `blocker` or `major` finding spends one loop of `autonomy.max_loops` (kind `feedback`, decision 15); a minor-only round spends none. The feedback review event does not move the review and ship gates, so the update goes build, verify, review, ship (`ship plan --update`) without any special path.
- **Human checks.** `confirm CHK-n` appends a `confirm` event and a `human` evidence record whose `human_heads` are the HEADs of every planned repo; any new commit asks again. `verify` reports the check as `pending` and stays exit 0 (a pending check is the user's turn, not a failure); `gate verify` fails with `waits for the user's confirmation`, so no review can be recorded, which is why a pending check never spends a review loop. A bug AC whose only checks are human is refused at `gate plan`; a design AC keeps its `visual` and `style` rule.
- **Quality baseline.** The baseline is a `baseline` event (the run keeps no `baseline/` folder), keyed by check, spec hash and branch point. `verify` takes it the first time; `factory baseline [--fresh]` takes it on request. Two agreeing runs end the 3 runs. A failing exit without any id is the id `exit:<code>`. Setup and zero-test results are never a baseline. Quality checks are allowed in plan.json and as `[[repo.check]] type = "quality"`.
- **Scoped.** `verify --scoped` runs the `scoped` template with the files added, copied, modified or renamed in `branch_point..HEAD`. The record carries `details.scope = "scoped"` and is ignored by every gate, so the full command always runs before `gate review`.
- **Guidelines.** A `[[repo.check]]` with `kind = "guideline"` and `text` is not a check. The `code` review must list one `guidelines` entry per rule of the planned repos (`followed`), and cannot APPROVE a rule it marks as not followed.
- **Risk.** `notes/design.md` is required at `gate plan` for `medium` and `high` (it is not in the lock). `high` also needs different reviewer names on the latest `code` and `qa` reviews, checked by `gate review`; `next` says so.
- **Metrics.** `idle_hours` is a gap longer than `[metrics] idle_minutes` (default 30) with no open blocker; it is excluded from phase time. The phase list gains `feedback`, and a feedback round puts the clock back in `build`. `metrics --all [--since YYYY-MM-DD]` reads every run's events. `metrics --tokens --session <id>` runs the adapter and records a `tokens` event only when it reports something; session ids are limited to letters, digits, dot, dash and underscore.
- **Estimate.** `verify --estimate` takes the median of the check's earlier verify durations in this run, else in the project's other runs; a check with no history says so. Human checks are `ask`. It runs and records nothing.

Speed (the suite went from 115 s to about 80 s while it grew from 382 to 422 tests):

- `git.head` and a branch name are read from the git files (no process), `ahead` and `is_ancestor` are remembered per pair of commit ids, and read-only commands ask git for `dirty` once per question.
- The tests build a prepared project once per module and copy it back for each test (every case runs at one path per process, so recorded paths stay valid); `tests/durations.json` orders the modules slowest first.
