# dev.factory — design and contracts

Ticket in → work around `dev.mcp` (Jira, GitLab, Figma, Confluence) → complete delivery: reviewed MRs whose acceptance criteria, UI included, are **proven by executed evidence**, not by model claims.

Successor of dev.harness. Lessons that shaped it (see the dev.harness effectiveness audit of 2026-11-12):

- The model plans and delegates well on its own. Prose gates add cost, not proof. → **Thin prose, thick mechanisms.**
- PASS without execution was the main escape path. → **Only collectors write evidence; gates read only evidence.**
- Missing runtime environment ended every verify INCOMPLETE. → **Environment is codified and checked at plan time.**
- Work arrives as epics across repos and target branches. → **A run is a set of tickets × repos × targets, not one checkout.**
- Nothing was measured. → **Every run produces metrics.**

## 0. Threat model

The factory defends against two things:

1. **Accidental or lazy false PASS by a cooperative model**: claiming an AC or fix from reading code, a check that cannot fail, a setup failure taken for a reproduction, loosening a check or a cap to go green, a stale review or proof carried past a change.
2. **Workers exceeding their role**: a builder recording reviews, an author touching code, any worker changing run state, replanning, rewinding, deciding for the user or setting `FACTORY_ROLE`.

It does **not** defend against a deliberately adversarial orchestrator. All state (run.json, evidence, reviews, workspace.json, `remote/` readbacks) is local files writable by the same OS user that runs the main session; the hooks and digests stop mistakes and shortcuts, not a session determined to forge them. The main session is the trusted orchestrator: it never records reviews (only the factory-auditor does) and uses `run decide --by user` only for decisions the user actually stated in chat.

Mechanisms within this model: plan lock over the plan files and `workspace.json` (§2.6); reviews bound to the plan lock and current SHAs and re-checked at ship; `run replan`/`run rewind` need a recorded user decision (`--decision <n>`) or count against `autonomy.max_replans` / `autonomy.max_build_loops` and block the run; setup failures (exit 126/127/9009, command/file/module not found) are never a reproduction and `expect_fail_pattern` must name real text; env pids are killed or trusted only when their create time matches; pipeline waivers name the pipeline id and keep the user's words.

**Accepted residual risk** (out of scope by design):

- run.json / event forgery by the orchestrator (e.g. writing an evidence file and appending a matching digest event through Python instead of `factory prove`). Digests prove a file is what the CLI wrote, not who ran the CLI.
- `remote/` readbacks (MR, pipeline, discussions) written by hand instead of saved by a dev.mcp read with `save_to`.
- Untracked files hidden from `git status` by `.git/info/exclude` (or a global excludes file): `dirty` checks see only what git reports.
- `review record` trusts `FACTORY_ROLE=auditor` in its environment; the guard keeps scout, author and builder from mentioning it, and the main session is trusted not to use it. The stored `recorded_by` (Claude session/agent env hint, best effort) is an audit trail, not authentication.

**Future work:** tamper-proof proof needs `prove` (and the gates that read its output) to run in another trust domain, e.g. a GitLab CI job that collects the evidence and stores or signs it where the local session cannot write, with the MR pipeline as the authority.

## 1. Roles

| Layer | What | Where |
|---|---|---|
| Orchestrator | Main Claude session: decides, talks to the user, runs `factory` CLI, does every dev.mcp **write** and every `git push` | `claude/skills/factory/` |
| Workers | `factory-scout` (haiku, read-only lookups), `factory-author` (sonnet, plans/ACs/checks/diagnosis), `factory-builder` (sonnet, code), `factory-auditor` (sonnet/opus, review, never the author) | `claude/agents/` |
| Mechanism | `factory` CLI (Python ≥3.10 stdlib only) + `browser/` (Node ≥20, Playwright, pixelmatch) | `factory/`, `browser/` |
| Guard | PreToolUse hooks: worker role limits; nobody (main session included) writes evidence, reviews or run state by hand; among workers only the auditor may mention `FACTORY_ROLE` (needed by `review record`); no worker runs `run replan|rewind|decide|unblock` | `claude/hooks/` |

The CLI never calls the network except: local env health checks, local API checks against the run's env, and `git` on local repos. dev.mcp is the agent's tool; when a gate needs remote facts (MR state, pipeline, Figma payload), the agent calls the dev.mcp read tool with `save_to=<absolute path>` (the tool writes the raw response; the model never relays it) and the CLI validates that file. A failing gate or command prints the exact call (`FETCH <tool> k=v ...`, `fetch: [{tool, args}]` with `--json`).

## 2. Files and layout

`FACTORY_HOME` (env var; default `~/.factory`):

```
FACTORY_HOME/
  workspaces/<ws>/workspace.json     # per product (e.g. one per company/product)
  runs/<run-id>/                     # one per ticket or epic
    run.json                         # state; CLI-written only
    acs.json                         # acceptance criteria + checks; author-written, CLI-validated
    figma/<nodeId-dashed>.json|.png  # Figma pack (design-context payload + screenshot), agent-saved from dev.mcp
    figma/meta.json                  # {fileKey, lastModified, version} per file
    checks/                          # browser specs, style maps, api specs written by author/builder
    evidence/<check-id>.json         # collector-written only
    evidence/<check-id>/...          # screenshots, diffs, logs
    baseline/<repo>.json             # quality-command failures on merge-base, computed once
    reviews/<kind>-<n>.json          # recorded via CLI by auditor
    remote/                          # raw dev.mcp responses saved by the agent (mr-*.json, pipeline-*.json, issue-*.json)
    ship-plan.json                   # CLI-generated
    metrics.json                     # CLI-generated
  env/<ws>/<repo>.pid|.log           # processes started by `factory env up`; .pid = {pid, cwd, head, started, create_time}; slot k > 0: <repo>@<k>.pid|.log
  env/<ws>/<repo>[@<k>]/lease.json   # env lease of one repo slot (section 11); env/<ws>/lease.json is the legacy workspace lease
  secrets/<ws>.env                   # test credentials (never in chat, never in repos)
```

Run id: `<ws>-<ticket-key-lowercase>` (epic: the epic key), e.g. `acme-dev-9454`.

`autonomy.ship`: `"ask"` (Gate S in chat for every remote write) or `"draft-auto"` (push + create/update **draft** MRs without asking; un-draft, Jira comment and transition still ask). `factory workspace import --from <repo>/.dev/project.json` converts a dev.harness profile; missing `path`/`quality`/`env` are left for the user.

`rules[]` are repo conventions with an executable check; every rule check runs in `prove` for each touched repo.

`quality.setup` (optional) is not a quality command: it is the restore command every worktree gets before checks run, identically for the run worktree (`run branch`/`run mirror`/`--mr`), the baseline and REPRO temp worktrees, and both red-green worktrees. Without it, worktrees get a link to the main repo's `node_modules` (with it, no link: a restore through a junction would rewrite the main repo). A failing setup is an `error`, never a reproduction.

`limits` caps check thresholds (§2.3): a plan cannot loosen a visual or style check past them.

### 2.3 acs.json (author-written, CLI-validated)

```json
{
  "schemaVersion": 1,
  "acs": [
    {"id": "AC-1", "ticket": "DEV-9454", "text": "…", "kind": "ui|api|logic|data|bug", "source": "jira:DEV-9454#description",
     "checks": ["CHK-1", "CHK-2"]}
  ],
  "checks": [
    {"id": "CHK-1", "type": "test", "repo": "React", "cmd": "npx vitest run src/x.test.tsx", "expect": "exit0"},
    {"id": "CHK-2", "type": "browser", "repo": "React", "spec": "checks/browser/ac-1.spec.ts"},
    {"id": "CHK-3", "type": "visual", "repo": "React", "node": "3544:5710", "path": "/obras/1/tarefas", "selector": "[data-testid=drawer]", "viewport": [1440, 900], "max_diff_ratio": 0.02, "masks": [], "wait_for": "[data-testid=drawer]", "settle_ms": 300, "fit": false},
    {"id": "CHK-4", "type": "style", "repo": "React", "node": "3544:5710", "path": "/obras/1/tarefas", "map": "checks/style/drawer.json", "wait_for": "[data-testid=drawer]"},
    {"id": "CHK-5", "type": "api", "repo": "API", "method": "POST", "path": "/v2/campos", "body": {}, "expect": {"status": 201, "json": {"$.id": "exists"}}},
    {"id": "CHK-6", "type": "red-green", "repo": "API", "cmd": "dotnet test --filter X", "fix_commit": "<sha or HEAD>"},
    {"id": "CHK-7", "type": "human", "text": "Native screen picker cannot be automated", "reason": "…"},
    {"id": "CHK-8", "type": "screenshot", "repo": "React", "title": "Tarefas drawer", "spec": "checks/shots/drawer.spec.ts"}
  ]
}
```

Optional UI check keys: `adapter` (visual and style: run-relative JSON `{"actions": [...]}` of `goto` (same origin only), `click`, `fill`, `wait` steps run after the page loads and before `wait_for`, to reach a state such as an open drawer; `gate plan` rejects it on other check types and outside the run dir; the collector errors when the file is missing), `wait_for` (selector awaited before capture/probe; visual and style), `settle_ms` (extra wait after load; visual), `fit` (visual: pad both images to the larger width and height, no scaling, before comparing instead of failing on a size mismatch; the padded area counts as mismatched pixels). Before comparing, the collector crops the Figma png to the node's own box (bounds from `absoluteBoundingBox`/`absoluteRenderBounds`, else `size` plus shadow/blur effects, scale from the png width), writing `figma-cropped.png` to the evidence folder; with matching sizes or no bounds the original png is used.

`expect_fail_pattern` (regex): the output a check shows when it fails for the right reason (the test name or the assertion text). Required on every `test` check of a `kind: bug` AC and on every `red-green` check (on the check itself, or on its `of` test check). A non-zero exit whose output lacks the pattern is status `error` ("could not reproduce: setup failure"), never `fail`/`reproduced`. Optional on `browser`/`api` checks (matched against the failed test errors / response mismatch).

Plan-gate rules (`factory gate <run> plan`):

- Every AC has ≥1 check; every check is referenced by ≥1 AC; ids unique.
- `kind: ui` ACs need ≥1 `visual` **and** ≥1 `style` check; every `node` has a pack entry (`figma/<node>.json` + `.png` decodable) and `figma/meta.json` names its file revision.
- `kind: bug` ACs need a `red-green` check, **or** a runtime check (`browser`/`api`/`visual`/`style`) that has REPRO evidence `reproduced` at the merge-base and passes at HEAD (enforced at `gate prove`; §8).
- `browser`/`visual`/`style`/`api` checks need the repo's `env` block and `factory env check` capability (start command + health); missing env → gate fails with one consolidated list of what the user must provide.
- `human` checks are allowed but counted; the ship briefing lists them; they never satisfy a `ui` or `bug` AC on their own.
- Style maps: every expected value must match a value of the **same property family** in the node's pack JSON, so expectations come from Figma, not from the model: `fontSize` ↔ `fontSize` (also `style.fontSize`); `lineHeight` ↔ `lineHeightPx`/`lineHeight`; `fontWeight`, `letterSpacing`, `opacity`, `fontFamily` ↔ the same key; `borderWidth` ↔ `strokeWeight`; `text` ↔ `characters`; sizes (`width`, `height`, `padding*`, `gap`, `borderRadius`) ↔ `absoluteBoundingBox.width/height`, `width`, `height`, `padding*`, `itemSpacing`, `cornerRadius`; colors (`color`, `backgroundColor`, `borderColor`) ↔ paints under `fills`/`strokes`/`background`. A key with no family is rejected.
- Threshold ceilings (workspace `limits`, defaults `{"max_diff_ratio": 0.03, "max_tolerance_px": 2}`): a visual `max_diff_ratio` or a style `tolerance_px` (map entry or check) above them is rejected.
- Bug ACs: every `test` check needs `expect_fail_pattern`; every `red-green` check needs one (own or of its `of` check).
- On pass the gate writes the **plan lock** (§2.6).

### 2.4 Evidence record (collector-written only)

```json
{
  "schemaVersion": 1, "check_id": "CHK-3", "type": "visual", "status": "pass|fail|error",
  "repo": "React", "git_sha": "<HEAD of repo worktree at collection>", "dirty": false,
  "collector": "factory/0.1.0 visual", "started": "…", "duration_s": 12.3,
  "summary": "diffRatio 0.004 ≤ 0.02",
  "artifacts": ["evidence/CHK-3/app.png", "evidence/CHK-3/figma.png", "evidence/CHK-3/diff.png"],
  "details": {}
}
```

Collected with a dirty worktree → `status` may be pass but the prove gate rejects it. Dirty means `git status --porcelain --untracked-files=normal`: untracked files count (`.gitignore` is respected; the `node_modules` link `run branch` creates does not count).

Runtime checks (`browser`, `visual`, `style`, `api`) are bound to their env: `prove` writes status `error` unless the repo's env was started by `factory env up` from the check's worktree (`env.cwd` under it) at the current HEAD (REPRO: at the merge-base) and that process is still the one recorded (pid + create time).

Evidence ids: one record per check id; the quality-delta record of a repo is `QUALITY-<alias>` (type `quality`), and each workspace rule check is `RULE-<rule-id>-<alias>` for every touched repo it applies to. The prove gate requires all of them to be `pass`.

### 2.5 Review record (via `factory review record`)

```json
{"schemaVersion": 1, "kind": "code|qa", "round": 1, "verdict": "APPROVE|CHANGES", "reviewer": "factory-auditor", "repos": {"React": "<sha>"},
 "findings": [{"id": "F1", "severity": "blocker|major|minor", "file": "src/x.tsx:42", "text": "…", "ac": "AC-1"}],
 "completeness": {"done": 0, "gap": 0, "not_checked": 0}}
```

QA review must state, for every AC, whether its checks actually exercise the AC (a check that cannot fail is a finding). The record carries `"ac_coverage": [{"ac": "AC-1", "exercises": true, "note": "…"}]` with one entry per AC in `acs.json`; `review record --kind qa` rejects a missing entry, and `exercises: false` cannot be combined with `APPROVE`.

`review record` runs only with `FACTORY_ROLE=auditor` in its environment (the factory-auditor agent sets it in the command; `worker-guard.js` denies any mention of `FACTORY_ROLE` to scout, author and builder; `protect.js` does not check it, because settings hooks also run inside subagents and would block the auditor; the orchestrator never records reviews, §0). The stored review gets `plan_lock` (the plan-lock digest it was recorded against) and, when the host exports one, `recorded_by` (`CLAUDE_AGENT_ID`, `CLAUDE_SESSION_ID`, ...; best effort, omitted otherwise). `repos`, when given, must be an object `{alias: sha}` (a list or a string is refused with the expected shape); a claimed SHA matches the HEAD when it is the full SHA or a prefix of at least 7 hex characters, and the stored record always carries the full SHA; a real mismatch names the repo, the claimed and the actual SHA. `completeness` (integers `done`, `gap`, `not_checked`) is required; `APPROVE` is invalid with `gap > 0`, `not_checked > 0`, or any `blocker`/`major` finding. A `resolved` flag on a finding is ignored by `record`, the review gate and the review report: a finding is resolved only by a later round that no longer lists it. An optional top-level `resolved: [...]` (list of non-empty strings, otherwise `record` refuses it) lists findings of earlier rounds that are now fixed, each as `"<round>:<id>"` (auditors reuse ids, so round 1 `F1` is not round 2 `F1`; a bare id names only the round immediately before the one that lists it); the gate ignores it, and only `ship plan` reads it: the MR description's `## Follow-ups` collects the minor findings of every `code` and `qa` round, de-duplicated by file and text, drops those a later round of the same kind names in `resolved` (qualified by round as above) (absent means still open, so older review files behave as open follow-ups), and is capped at 20 items plus a count. `human` checks are not the auditor's `not_checked`: they are listed in the ship briefing. The CLI adds `recorded` (ISO time) to every stored review; `metrics` uses it to count findings that appear after the prove gate (escaped). The `review` event in run.json is `{review_kind, round, verdict, findings, digest, plan_lock[, recorded_by]}`; `gate_pass`/`gate_fail` events carry `phase`.

### 2.6 Proof integrity

- **Plan lock.** When `gate plan` passes, run.json gets `plan_lock = {at, seq, digest, files: {<path>: sha256}, workspace}` over `acs.json`, every file under `checks/` and `figma/`, and `diagnosis.md` when present; `workspace` is the sha256 of `workspace.json` as canonical JSON (key order and whitespace ignored; no volatile keys today). Any workspace change after the plan (caps, limits, quality commands) fails every later gate, before any loop/cap logic runs, with "workspace changed after plan; replan". `gate reproduce` refuses changes except `diagnosis.md` (written in reproduce) and then re-locks with it. `gate prove`, `gate review`, `ship plan`, `ship verify` and `gate ship` re-hash and fail listing the changed files. The one legit way to change them: `factory run replan <run> "<reason>" [--decision <n>]` (phase → plan, lock cleared, `replan` event, `loops.replan += 1`); the plan gate must pass again (re-running every acs.json validation), evidence written before the new lock (`seq` = event index) no longer counts, and reviews recorded against the old lock no longer count.
- **Replan/rewind authority.** `--decision <n>` names a decision recorded with `run decide … --by user --user-said "<gist>"` in the current phase; it is consumed (`used`) and the replan/rewind does not count against a cap (`loops.replan_approved += 1` for replans). Without it, a replan counts against `autonomy.max_replans` (default 2) and a rewind counts into `loops.build`; past `max_replans` / `max_build_loops` the command refuses, the run is blocked (question blocker, resumes in the phase it was in) and the user decides.
- **Proof at HEAD.** The review gate, `ship plan`, `ship verify` and `gate ship` re-run the prove-gate criteria (evidence pass, not dirty, `git_sha` == current HEAD, quality/rules, plan lock) without collecting anything: a commit after prove fails them. `gate prove` records `proved = {alias: {target|"HEAD": sha}}`. `ship plan` records each MR's `head_sha` (tip of its source branch); `ship verify` requires the branch still there and the readback `sha` (or `diff_refs.head_sha`) equal to it. After a rebase/merge or late fix: `factory run rewind <run> build|prove "<reason>" [--decision <n>]` (`rewind` event; `loops.build += 1` without a user decision). `ship verify` and `gate ship` also re-check that the latest `code` and `qa` reviews are `APPROVE`, digest-intact, bound to the current SHAs and the current plan lock.
- **Reproduction is an assertion.** A failing side (repro on base, red side of red-green) is `error`, never `reproduced`/red, when the exit code is 126, 127 or 9009, when the output shows a setup marker (`command not found`, `is not recognized as an internal or external command`, `ENOENT`, `No such file or directory`, `Cannot find module`, `could not find a part of the path`, `MSBUILD : error MSB1009`, `ModuleNotFoundError`; on Windows also cmd.exe's localized `'<cmd>' …` line), or when `expect_fail_pattern` is not in the output. The plan gate (and repro) reject an `expect_fail_pattern` shorter than 6 characters or with fewer than 4 literal word characters (`.`, `.*`, `\w+`, `[a-z]{6}`).
- **Env identity.** `env down`, `env up` (stale restart) and evidence binding act on a recorded pid only when its stored create time equals the live one. When either cannot be read (legacy record, OS refusal), the CLI neither kills nor binds: it reports and asks the user.
- **Digests.** Every evidence file `prove` writes gets an `evidence` event `{check, status, sha, digest}` (sha256 of the file); every review file `review record` (and `feedback ingest`) writes gets a `review` event with `digest`. Gates and the review report refuse an evidence/review file whose bytes do not match its latest event, or that has no event (hand-written even when `protect.js` is bypassed).

## 3. CLI contract

`python -m factory <command> …` (installed shim: `factory`, which runs the installed snapshot, see section 5). Exit 0 = OK, 1 = gate/check failed, 2 = usage/config error. Every command prints a short human summary; `--json` prints machine output.

| Command | Owner module | Effect |
|---|---|---|
| `workspace init <ws>` / `workspace import <ws> --from <project.json>` / `workspace check <ws>` | `commands/workspace.py` | create/convert/validate workspace.json |
| `run start <ws> <TICKET...> [--epic KEY] [--risk high] [--bug KEY]... [--login-user EMAIL]` | `commands/run.py` | create run dir + run.json (phase intake) |
| `run status <run>` / `run list` | `commands/run.py` | phase, loops, blockers, next required action |
| `run branch <run> <repo> --base <target> [--name …] [--from-run <child-id>]` | `commands/run.py` | create worktree + branch under worktree_root, record in run.json; `--from-run` stacks on that run's branch of the same repo (records `base_branch`, `base_run`) |
| `run start … --hotfix` / `run mirror <run> <repo> --to <target>` / `run mirror-diff <run> [--json]` | `commands/run.py`, `mirrordiff.py` | hotfix run, cherry-pick mirror worktree, and the read-only same-changes comparison of the mirrors (§9) |
| `run branch <run> <repo> --base <target> --env-only` / `run env-only <run> <repo> [--off]` | `commands/run.py` | a repo registered only so `env up/check/login --run` start it from a run worktree, with no code: `repos[alias].env_only: true` (`run env-only` marks or unmarks an already registered repo, at any phase, with an `env_only` event and no replan). `core.code_repos(run)` is every repo except env_only ones; `gate build` (commits, dirty, header/trailers), `gate prove`/`review` (touched repos, quality and rule checks, dirty, review head binding), `prove` repo selection, `review record`, feedback shas, `run mirror`, the UI-repo/diff detection of `shots` and `ship plan`/`verify` (no push, no MR) use only code repos. A dirty env_only worktree (local config kept on purpose) blocks nothing. ## 4. Collectors

`factory/collectors/<type>.py` exposes `collect(check: dict, ctx: Ctx) -> dict` returning the evidence record body (`status`, `summary`, `artifacts`, `details`); `prove` fills common fields and writes the file through `core.write_evidence`.

| type | Implementation |
|---|---|
| `test` | run `cmd` in repo worktree (shell, timeout), exit code, tail of output |
| `red-green` | temp worktree at `fix_commit~1` with the test files from `fix_commit` → must fail; at `fix_commit` → must pass. `cmd`, or `of: <check-id>` to run another `test` check in those worktrees (§8) |
| `api` | env must be up; urllib request to `base_url + path`; status + simple JSONPath (`$.a.b`, `exists`/literal) |
| `browser` | `node browser/dist/cli.js run-spec --spec … --base-url … --storage-state … --out …` (Playwright test runner, JSON reporter) |
| `visual` | `node browser/dist/cli.js capture …` then `compare --figma figma/<node>.png …` (pixelmatch; copy check; masks) |
| `screenshot` | `path`: `capture` only (no compare); `spec`: `run-spec … --screenshot on`, every PNG under `artifacts/` is an artifact. Pass = images captured (and, at HEAD, the steps passed). Visual evidence the user asked for (§12), never an assertion |
| `style` | `node browser/dist/cli.js style-probe --url … --map … --out …`: getComputedStyle + bounding box per selector vs expected values with tolerance (px ±1 default, colors exact after normalisation) |

The Python wrappers for `browser|visual|style` live in `factory/collectors/` and shell out to Node; they never decide pass/fail themselves beyond reading the Node result file.

## 5. Host integration (Claude Code)

- Skill `factory` (model-invocable): entry for any ticket/epic URL or key; the runbook of phases, which worker does what, when to call which CLI command, and the stop rules. Target ≤150 lines; details in `references/`.
- Agents `factory-scout|author|builder|auditor` with role guard hooks.
- Hook `protect.js` (installed in the profile's settings for **all** sessions): deny Write/Edit/NotebookEdit and shell redirection into `FACTORY_HOME/runs/*/{run.json,evidence/**,reviews/**,baseline/**,metrics.json,ship-plan.json}`. A shell command is decided **safe by construction**, not by listing dangers: `deny = extra || ((baseline || coarse) && !provablySafe)` (`claude/hooks/protect-lib.js`, shared by `worker-guard.js`). `baseline` is the coarse logic as it was before the write-target rule, embedded byte-identical to the frozen test oracle `claude/hooks/test/fixtures/protect-lib.baseline.js`: a non-read-only, non-factory part of the command mentions a run path and carries a write-capable verb, or a modelled destination is protected, or interpreter code writes a run file. `coarse` is the same net with what came later (the bare `factory` name only, the longer verb list, a variable assigned a run path, `eval`). `extra` are the precise per-target rules that only ever add denials (redirection, `tee`, in-place editors, `sed w`/`awk >` scripts, process substitution, text piped into a shell or interpreter, `git` with a protected cwd/`-C`/`--work-tree`/`GIT_*`, `python -m zipfile|shutil|...`, compressors, `patch`, PowerShell writers, odd spellings that normalise onto a protected file, `cd`/`Push-Location` inside subshells and groups); a nested body (`bash -c`, `$(...)`, `factory wait --cmd`) gets the whole decision. `provablySafe` is a short **positive grammar over the whole command**: the coarse verdict is lifted only when every part parses into it. (1) The text has no substitution, process substitution, glob, brace, paren, `#`, `!`, `^`, `@`, lone `&`, heredoc, unknown variable, `~user` or PowerShell lookalike quote/dash; a variable (`$HOME`, `$env:USERPROFILE`, `%USERPROFILE%`, `$FACTORY_HOME`...) or a leading `~/` may start a word only where it is read; an unquoted `\` is read both the bash way (escape) and the PowerShell way (plain) and both readings must pass; a word that PowerShell would split (`"a"/b`) is allowed only as a read. (2) Every command word is a bare name from fixed lists: readers (`cat`, `head`, `tail`, `grep`, `jq`, `wc`, `ls`, `stat`, `echo`, `Get-Content`, `Select-String`, `Get-ChildItem`, `Test-Path`, `Get-Item`...; `sort`, `diff`, `gzip -c` with listed flags only), copiers (`cp`, `rsync` with listed flags: no link, target, move, delete, backup, log or remote-shell flag; sources are read, the last operand is written; PowerShell's `cp` with one operand is refused), writers (`rm`, `rmdir`, `mkdir`, `touch`, `mv`, `sed [-i] s/a/b/[gI]`: every operand is written), `cd`/`pushd`/`Set-Location`/`Push-Location` to an absolute literal path with no run path, `git [-C <absolute>] status|log|diff|show|branch|rev-parse|ls-files|checkout|switch|add|commit` (no `-c`, `--work-tree`, `--git-dir`, `--output`; a writing subcommand needs the repository around every possible cwd to lie outside the guarded tree), `factory`/`python -m factory` (arguments are data) and `python -c` code that cannot write (ASCII, `json`/`sys`, `open()` with one literal, names from a short list). Functions, aliases, `set --`, `xargs`, `find -exec`, `eval`, `source`, `env`, shells, other interpreters, loops and anything else are not in the grammar. A writer or copier never follows a pipe (PowerShell binds piped objects to path parameters). (3) Relative write targets are resolved against the session cwd and every directory the command changes to. (4) A run path may appear only as a reader operand, a copier source, factory CLI or read-only `python -c` data; a run path in the raw text that no single word names (split by a space) is refused. (5) Every write target (redirection, copier destination, writer operand) is a strict literal (no quoting tricks, variable, `\`, `..`, `//`, stream, short name, trailing dot or space, comma) whose lexical path AND real path (nearest existing ancestor through `fs.realpathSync.native`, so junctions such as `C:/Documents and Settings` and symlinks resolve; a dangling link is refused; on Windows `/x/...` is also read as `X:/`, `/mnt/x/`, `/cygdrive/x/` and Git Bash `/tmp`) is not a factory home (FACTORY_HOME, `~/.factory`, and their real paths), an ancestor of one, its `env/` folder, a protected run path or the run folder above it; unprotected run files (`runs/<id>/remote/`, `notes/`) may be written by such a literal. Heredoc text is data only in one shape: the whole command is `<first line> <<DELIM` + body + `DELIM`, the heredoc feeds `cat` (no operand), `tee`, `git commit|tag -F -`, `gh ... --body-file -` or the factory CLI, and an unquoted DELIM has no `$`, backtick or `\` in the body; the first line (with an optional `> file`) is then judged in full. Known false positives that stay denied (outside the grammar on purpose): `python -c` that is not in the read-only subset, `node -e`, a run path in a `git commit -m` message, `sed -i` with `$(...)`, `Copy-Item`/`copy`/`xcopy`/`robocopy`/`install` reading a run file, any command written with `\` in a write target, `cd` to a relative path. Known limits: hard links are invisible to the real-path check (creating one to a protected file is denied), writes through a pre-existing junction whose spelling never names a run path are not caught (the baseline did not catch them either), the MSYS mount table other than `/tmp` and the drive forms is not consulted.
- **Installed snapshot.** The `factory` shims never put the repo working tree on `PYTHONPATH` (sessions edit the repo while runs are live; a half-edited module or an unmerged branch must not reach a run). `install.py` copies what the CLI reads at runtime into `<profile>/factory-dist/`: `factory/` (no caches), `browser/dist` and `browser/package.json`, `browser/node_modules` (a symlink, or a junction on Windows, to the repo's; a full copy when linking fails; nothing is downloaded), and `provenance.json` `{source, sha, dirty, state, dist_stale, installed_at}` (`state` is a digest of HEAD plus the diff and untracked content of the runtime paths, so an install from a dirty tree is "behind" only once those files change again; `dist_stale` is set when a `browser/src` .ts is newer than the gitignored `browser/dist`: the installer warns and the notice repeats it, the build is never run automatically). The only repo-root-relative lookups (`factory/collectors/browser.py` `FACTORY_ROOT`, `factory/commands/env.py` `factory_root()`) resolve to the parent of `factory/`, so they find `browser/dist/cli.js` inside the snapshot; `scripts/`, `claude/` and `tests/` are not needed at runtime. The snapshot is built in `factory-dist.new`, the previous one moves to `backups/factory-<timestamp>/factory-dist` (without its `node_modules`) and the new one is renamed in; the snapshot and the shims are the first install step (a snapshot that cannot be replaced, e.g. locked by a process whose cwd is inside it, stops `install.py` with the path and what to close before hooks or settings change; old shim and old snapshot keep working together), the swap happens first and the old snapshot's `node_modules` link is pruned afterwards, best effort, never followed; a failure keeps the old snapshot. Repo changes take effect only after `install.py` is re-run. `FACTORY_SRC=<checkout>` makes both shims run that source tree instead (live testing of a branch). The shims start Python with `-c` and drop every cwd entry from `sys.path` (`''`, `.`, and the absolute cwd that an empty `PYTHONPATH` item resolves to; the cmd shim also builds `PYTHONPATH` without an empty item) unless the cwd is the chosen root, because `python -m factory` run from inside a checkout would otherwise import the working tree. Both shims exit 2 with `factory: no factory/ package in <root>` when the chosen root (snapshot or `FACTORY_SRC`) has no `factory/cli.py`; a missing root never falls back to the cwd. `factory.cmd` limit: unquoted `&`, `|`, `^`, `%VAR%` in arguments are re-parsed by cmd (`%*`); quote them. `factory --version` prints `factory <version> (snapshot <sha>[+dirty], installed <ts> from <repo>) at <path>` or `(source <sha>) at <path>`. `--version` and `run status` (the one frequent, cheap entry point; every other command stays free of git calls) also print `installed snapshot is behind source (run install.py)` to **stderr** when the recorded source repo has another HEAD or its state under `factory/`, `browser/src` or `browser/package.json` differs from the installed `state`; never fatal, never on stdout, so `--json` stays parseable. Hooks and agents call `factory` or hook files in the profile and carry no repo path.
- `install.py --profile <dir> [--remove-harness] [--dry-run]`: copies/links skill, agents, hooks into the profile, merges hook entries into `settings.json`, writes the delegation snippet into the profile's `CLAUDE.md` between markers, creates `FACTORY_HOME`. `--remove-harness` removes `dev-*` skills/agents/hooks and the harness block from `CLAUDE.md` (backup first).

## 6. Epics

An epic is a **parent run** that coordinates **one child run per ticket**. Children have their own phase, gates, evidence, worktrees and loops; a blocked child never blocks children that do not depend on it.

- Parent id: `<ws>-<epic-key>`; child ids: `<ws>-<ticket-key>`. Parent `run.json` adds `"kind": "epic"` and `"children": ["<child-id>", …]`; child adds `"parent": "<parent-id>"`. Plain single-ticket runs have `"kind": "ticket"`.
- `epic.json` in the parent dir (author-written, CLI-validated): `{"schemaVersion": 1, "tickets": [{"key": "DEV-9451", "repos": ["API", "React"], "depends_on": ["DEV-9450"], "summary": "…", "area": "…"}]}`.

| Command | Effect |
|---|---|
| `epic start <ws> <EPIC> --tickets K1 K2 …` | parent run (phase intake) + child runs (phase intake), cross-linked |
| `epic plan <parent>` | validate epic.json (unknown keys, cycles, repos unknown to workspace, every child present), copy depends_on/summary/area into children, compute `waves` (topological levels) into parent run.json |
| `epic status <parent> [--json]` | matrix child × phase × loops × open blockers × MR readbacks; prints the next **ready** children (all deps in phase ship/done) |
| `epic ship plan <parent>` / `epic ship verify <parent>` | aggregate children's ship plans into one ordered action list (waves order, then repos order, then targets), Depends-on links across children, one epic Jira comment (workspace epic ship_comment when set); verify = every child ship verify OK |
| `gate <parent> <phase>` | parent phases: intake → plan → build (children running) → ship → done; leaving build requires every child in phase ship-ready (review passed) or done; leaving plan requires `epic plan` OK and each child's plan gate passed |

`epic plan` also writes `wave`, `planned_repos` and `stack_from` (`{repo: child-id}`, the dependency child to pass to `run branch --from-run`) into each child, and `waves`/`epic_plan` into the parent. A child is **ready** when it is not in ship/feedback/done/blocked and every `depends_on` child is in ship, feedback or done. `epic ship plan` refuses while any child is before ship; it builds each child's own plan (writing the child `ship-plan.json`, which `ship verify` reads), then writes the parent `ship-plan.json` with `mrs[]` (each with `child` and cross-child `depends_on`; descriptions gain `Depends on {mr_url:<child>:<repo>:<target>}`) and `actions[]` (push/mr/readback per MR, one epic Jira comment, child transitions). Parent gates: intake needs children; plan needs epic.json valid and applied and every child past its plan gate; build needs every child in ship/feedback/done; ship needs every child `ship verify` OK; then `done`.

Branches: a child that depends on another child in the same repo branches from that child's branch (stacked), recorded as `base_branch` in the child repo record; `run branch` accepts `--from-run <child-id>`.

## 7. Review runs (reviewing work that already exists)

For MRs the factory did not build: someone else's MR, the user's earlier work, tickets already in code review. Same machinery, different entry and exit; **read-only by default, nothing posted remotely unless the user approves**.

- `run.json` `"kind": "review"`; `"mrs": [{"repo": "React", "iid": 669, "source_branch": "…", "target_branch": "pack", "head_sha": "…", "ticket": "DEV-9431"}]`. Several MRs → a parent review run with one child per MR (reuse §6 parent/children; `"kind": "review-batch"`).
- Ticket ACs, not the diff, are the reference: the author writes `acs.json` from the ticket (and Figma), then checks; the diff is reviewed against them.

| Command | Effect |
|---|---|
| `review queue <ws> --mrs-json <file> [--me <username>]` | the agent saves `gitlab_list_merge_requests` responses (reviewer = me, state opened) to a file; CLI filters out drafts, MRs the user already approved (when approvals are present in the payload) and MRs authored by the user, maps each to its ticket key (title/branch/description regex from the workspace or `[A-Z]+-\d+`), prints the queue |
| `review start <ws> --mr <alias>!<iid> … [--ticket KEY]` | review run (or review-batch parent + children); records MR facts from `remote/mr-<alias>-<iid>.json` the agent saved |
| `run branch <run> <repo> --mr <iid>` | detached worktree at the MR head (`git fetch origin <source_branch>` done by the orchestrator first); builders are not used; `dirty` is checked as usual |
| `review report <run>` | verdict per MR: `ok` / `not-ok` / `incomplete`, with findings (severity, file:line, AC), ACs × evidence, `human` checks, freshness (behind-count vs target, unmerged deps), and what could not be verified; writes `review-report.json` + `.md` |
| `review fix <run>` | converts the run into `kind: ticket` on the MR source branch (worktree re-created as a normal branch worktree), keeps acs/evidence/findings, phase → build |

Implementation notes: `review start` takes the saved payloads with `--from <folder-or-file>` (the run folder does not exist yet; payloads are copied to `remote/mr-<alias>-<iid>.json`), `--mr alias!iid[=TICKET]`; run ids are `<ws>-<ticket>-review` and batch parents `<ws>-review-<stamp>`; the batch parent has phases intake → report → done (`gate report` needs every child done; `review report <parent>` aggregates). `gate <run> review` for a review run only needs both reviews recorded and bound to the MR head (a `CHANGES` verdict is a report result, not a loop to build). `review fix` converts in place with `git checkout` in the same worktree (no worktree removal) and refuses a dirty worktree or a local branch that is not at the MR head.

Phases for `kind: review`: intake → plan → prove → review → report → done. No build, no ship. `gate <run> report` requires `review report` written. Remote actions after report (MR comment with the findings, approval, Jira comment) are listed in the report with `needs_user: true` and are never pre-authorised by `autonomy`.

## 8. Bugs

A run is a bug run when a ticket is `type: bug` (`run start --bug KEY`). Phases: intake → plan → **reproduce** → build → prove → review → ship → feedback → done. The plan gate is unchanged except that it advances to `reproduce`; `gate build` in `reproduce` is refused (wrong phase). Feature runs have no `reproduce`.

- **Author** writes, in plan: reproduction checks (`test`, `api` or `browser` checks that FAIL on the unfixed code, referenced by the `kind: bug` AC), a `red-green` check for the fix (`cmd`, or `of: CHK-n` pointing at the reproduction `test` check), and `diagnosis.md` (run dir root) with `## Root cause`, `## Evidence`, `## Ruled out`.
- **`factory prove <run> --repro [--check CHK-n] [--assume-env]`** runs every non-`red-green`, non-`human` check referenced by a `kind: bug` AC against the base: the merge-base of the run branch with `origin/<base>` (falls back to the local base), in a temp detached worktree (the same helper as `baseline`, prepared with `quality.setup` like every worktree). It writes `evidence/REPRO-<check-id>.json` (CLI only; `protect.js` already denies `evidence/**`) with `status`: `reproduced` (check FAILED on base **on its assertion**: `test` output matches `expect_fail_pattern`; a `browser` spec has a failed test whose error is an assertion (`expect(`…) or matches the pattern; an `api` check got a response that mismatches), `not-reproduced` (it passed), `error` (could not run, or failed for another reason: "could not reproduce: setup failure"). `git_sha` and `merge_base` are the merge-base sha. Exit 0 only when all are `reproduced`.
- Checks must be runnable on the base without the fix (an existing test, or a script that does not need branch changes). `test` checks run in the temp worktree. `api`/`browser` checks need a running env, which serves the run worktree, not the temp one: they run only with `--assume-env`, and only if the run worktree is clean and still at the merge-base (before any fix commit), otherwise status `error`. `visual`/`style` cannot be reproduced.
- **Gate `reproduce`:** each bug AC has a check with REPRO status `reproduced` and `git_sha` equal to the current merge-base; `diagnosis.md` exists with the three sections non-empty (structure only; the code auditor judges the content); runtime repro checks need the repo env (the same consolidated env message as plan). No builder touches code before this gate passes.
- **Build:** the builder fixes the cause named in `diagnosis.md`. The code auditor must state whether the fix addresses the root cause and files a finding if it only masks the symptom.
- **UI bugs (no red-green):** a `kind: bug` AC may use a runtime check instead of `red-green` (`of` only supports `test`). The author writes a `browser` spec (or `api` check) that fails on the unfixed code. Order matters: the orchestrator brings the env up from the clean run worktree **before any build** (`factory env up --run`) and runs `factory prove <run> --repro --assume-env` (`reproduced`), then the builder fixes; `prove` later must pass the same check at HEAD. `gate prove` enforces for bug ACs without `red-green`: ≥1 runtime check with `REPRO-<id>` `reproduced` and bound to the merge-base, plus the normal passing evidence at HEAD. `visual`/`style` cannot be reproduced on base, so they cannot satisfy this alone.
- **`red-green`:** `fix_commit` (default `HEAD`) is the commit that contains the fix. The test may be in the same commit (its test files are found in that commit's diff) or in an earlier commit (then set `test_files`; the red worktree at `fix_commit~1` already has it). Both worktrees get the same preparation (`quality.setup` or the `node_modules` link). The red side must fail with `expect_fail_pattern` in its output, else `error`. `red-green` is optional for a bug AC that uses the repro + runtime path above.
- **`red-green` with `of`:** `of` references a `test` check of the same repo (validated at plan; `cmd` and `of` are exclusive). The collector runs the inner check in the `fix_commit~1` worktree (with the test files from `fix_commit`; must fail) and in the `fix_commit` worktree (must pass), through the `test` collector with `ctx.repo_path` set to the temp worktree. `browser`/`api` inner checks are not supported: the env would have to be started from the temp worktree, so plan rejects them. Use a `test` check for red-green (a `browser`/`api` check can still be the reproduction). Evidence details carry `of`.

## 9. Hotfix

Only when the user asks for a hotfix (homolog + pack in one go). One run, bug semantics (reproduce phase, §8), two targets, homolog first.

- **Workspace:** `ship.hotfix = {"base": "homolog", "mirror": ["pack"]}` (default when absent but a target named `homolog` exists; `workspace check` validates that base and mirrors are in `ship.targets` and the base is not a mirror). `ship.package` (optional, e.g. `"REL_9"`). Top-level `branch_format = {"feature": "…", "bug": "…", "hotfix": "…"}` with placeholders `{key} {slug} {target} {target_upper} {package}` (`slug` = summary slug, else repo alias slug; `target` = the `--base` / mirror target). `run branch` uses it when `--name` is absent (hotfix runs use `hotfix`, falling back to `bug`; no format → the legacy `bugfix|feature/KEY-alias`).
- **Per-repo target branches:** a repo entry may carry `target_branches: {"<target>": "<git branch>"}` when a logical target is a different branch in that repo (e.g. `pack` is `pack` in React but `dev` in the API). Targets stay logical everywhere in factory (run.json `targets`, evidence ids `CHK-n@pack`, gates, ship ordering, branch names from `branch_format`); only the git refs translate, through `core.target_branch(ws, alias, target)`: the base of `run branch` (and `--for-target`), `run mirror` (merge-base base ref and the branch the mirror worktree starts from), `resolve_base` for the merge-base, baseline and `prove --repro`, the build gate's ahead-of-base check, the `ship plan` behind-count against `origin/<branch>`, and the MR `target_branch` (compared again by `ship verify` against the readback). Without the field a target is its own branch name. Review runs are exempt (their base is a real MR branch). `workspace check` requires an object whose keys are known targets (`ship.targets` or the hotfix base/mirror) and whose values are non-empty strings.
- **`run start <ws> KEY --hotfix [--feature]`:** tickets are bugs unless `--feature`; run.json `hotfix: {base, mirror}` and `targets = [base, *mirror]` in that order. Branch the base target normally: `run branch <run> <repo> --base homolog`.
- **`run mirror <run> <repo> --to <target> [--name …]`:** requires `gate build` passed and a clean base worktree. Creates a worktree `<run>-<repo>-<target>` from `origin/<target_branch(repo, target)>` (local fallback; the target itself when the repo has no mapping) on the branch from `branch_format`, cherry-picks `merge-base..branch` of the base target in order, records `repos[alias].branches[target]` and `worktrees[target]`. On conflict the worktree stays mid-cherry-pick, a blocker of kind `conflict` (with `files`) is recorded, with a `block` event like `run block` writes (as does the automatic `question` blocker of a capped loop), and the command exits 1: a builder resolves, `git add`, `git cherry-pick --continue`, then `run unblock`. Never `--abort`/reset.
- **Evidence per target:** `prove` runs every check in each target worktree; ids are `CHK-n@<target>` and `REPRO-CHK-n@<target>` (repro on each target's merge-base; mirror merge-base = the target tip, so mirror repro is `test` checks only, runtime checks are reproduced on the base target). `gate reproduce` and `gate prove` require every target (a missing mirror worktree is a failure). Quality delta and rule checks stay on the base target worktree. Non-hotfix runs keep plain ids. Runtime checks on a mirror run against an env started from the mirror worktree: `factory env up <ws> <repo> --run <run> --target <mirror>` serves, for every repo that has a worktree for that target (`core.target_worktree`), that worktree; a repo without one keeps the run's resolution, except that the repo's `target_paths[<target>]` (workspace.json, a directory) is used when present. `--target` must be one of the run's targets (usage error otherwise); the base target or no flag is today's behaviour. The pid record carries `target` and `run` (the id of the run that started it with `--run`; absent when started without one, and in records written by older versions); `env check` prints `(target <t>)`, and a stale restart (`restart_env`, `env check --auto-restart`, `prove` preflight) restarts the same target. Switching target: `env up` refuses while the running env serves another worktree (`kind=stale`), so run `env down <repo> --run <run> --target <current target>` first: it stops the repo and also its `depends_on` repos whose record carries that target and this run's id (a dependency with another run's id or none, a shared one, or one started for another target stays up, reported as `left running (run <id>)`), then `env up ... --target <next>` (or without `--target` for the base). `prove --target` and `env check --auto-restart` switch on their own. A stale env counts as the run's own (`restart_blocker`) only when it is served from this run's worktree for that repo and target, or its record names this run (`run`) and its cwd is what one of the run's targets resolves to (a `target_paths` directory, a dependency's main checkout); an env without a run id or with another run's, started by hand or by another run, is refused as before (`env serves ... (run <id>|none)`), also when it serves a dependency run's worktree of an epic child. Restarts go dependencies first, in `depends_on` order (not alphabetical), and `env check --auto-restart` with `--target` restarts the stale `depends_on` closure of the repo first (only the run's own; otherwise it reports the blocker and leaves the repo alone). The lease rules still apply on top. `factory prove <run> --target <t>` runs only that target's evidence ids (runtime and test checks); quality and rule checks run only for the base target and are skipped for a mirror; `--estimate` honours it; `gate prove` still requires every target. `env login` accepts `--target` for symmetry (it only validates it). **MR ticket per target:** a hotfix run with several tickets titles every MR with the first ticket unless `factory run target-ticket <run> <target> <KEY>` stores `hotfix.tickets[target]` (hotfix runs only, target and KEY must belong to the run, logged as a `target_ticket` event, not allowed once the run is done or blocked); `ship plan` then builds that target's title (key, summary, area) from that ticket; re-run `ship plan` after changing it.
- **Mirror diff gate (same changes on every target):** per code repo and mirror target, `factory/mirrordiff.py` compares the net change of the base branch (`merge-base(base target ref, HEAD)..HEAD` of the run worktree) with the net change of the mirror branch (`merge-base(mirror target ref, HEAD)..HEAD` of the mirror worktree), as `git diff --no-renames -U0` per file (paths from `--raw -z`, never parsed from quoted headers; a mode-only change has no hunks and is ignored). A mirror not created yet is skipped. Files are matched by path, except that a file moved between the two target branches (`git diff -M` base target tip vs mirror target tip, limited to the paths of the two net diffs, plus the files named by the import lines of the two net diffs, found by `**/<module>.*` pathspecs, since an imported module that moved is usually in neither net diff) is the same file. **Rules.** (1) The changed lines decide: per matched file the removed and added lines must be the same after normalisation; whitespace is never ignored. (2) Import normalisation: in an import-like line (`import ... from "x"`, `} from "x";` continuation lines, `export ... from`, `require("x")`, `import("x")`, `#include "x"`, python `from x import` / `import x`; C# `using X;` has no path and is not touched) the module specifier is masked on both sides when its last segment, without extension, names a file moved between the two target branches (so a file that did not move but imports a moved module by another specifier passes); a specifier change with no moved file behind it is a divergence. (3) Placement is the git function context (text after the second `@@`) of each hunk, not the neighbouring lines (`-U0`, so hunk grouping never depends on the code around): the same changed lines in the same function context are equal whatever the neighbours; in a different non-empty context they diverge ("same lines, different place/context", the report shows both contexts); with an empty context on either side, and for hunks whose changed lines are only import statements and blank lines (or names inside an import list under an import context line), the context is ignored and the changed lines alone count. Hunks left over because git grouped the same lines differently still match inside each non-empty function context as a multiset, import-only ones pooled. The diff is read as bytes (no newline translation, no strip, utf-8 with surrogateescape): a CRLF vs LF difference or a trailing space is a divergence (excerpts then show `\r`); with `core.autocrlf` or `.gitattributes` normalisation the committed blobs are what is compared, so a Windows checkout of identical commits does not fail. In a file that sits at another path on the mirror, quoted relative paths (`'./x'`, `"../y/z"`) and python `from .x import` are masked before comparing. Whitespace is never ignored (a reformat must show), and `git patch-id` is not used because it ignores whitespace. Known limits: where the mirror target legitimately puts the change in another function the gate fails and needs the user exception; masking hides which module a relative import points to in a moved file, and a moved module is recognised by file name (git rename detection) so two modules with the same name are not told apart; import lines naming a module that did not move are compared exactly (a path adapted there needs the exception); a changed line moved within one function, or anywhere when git prints no function context, is not seen; the regrouping fallback accepts changed lines moved within one non-empty function context, and a file with no text hunks (binary, empty) is compared by blob id. Divergence lists per repo/target/file the hunks only on the base, only on the mirror (excerpts capped), and files changed on one side only, then the refs and merge-bases used (`origin/<target>` is preferred without fetching; a hint says to fetch when the local and origin target refs differ). A comparison error (missing ref, git failure) fails the gate and no allowance covers it. It runs in `gate prove` (the first gate that sees a mirror in the normal flow, since `run mirror` needs `gate build` passed and `gate build` only runs in phase build), again in `gate build` (after a rewind) and in `ship plan` (hotfix runs only), and read-only as `factory run mirror-diff <run> [--json]` (exit 0 equal, 1 divergent, 2 not a hotfix or no mirror yet). **Exception:** a user decision `mirror diff: <reason>` (`run decide --by user --user-said`), passed as `--allow-mirror-divergence <n>` to `gate build`, `gate prove` or `ship plan`, is stored once as `run.json` `mirror_allow = {decision, reason, digest, files}` (an `mirror_allow` event); the digest covers the whole current divergence (every repo/target/file/hunk), so any change to it invalidates the allowance and the gate fails again, and the decision is re-validated (exists, by user, prefix) on every check. The mirror MR description gets a `Mirror divergence (approved by the user)` section with the reason and the files. Tests: `tests/test_mirror_diff.py`.
- **Ship plan:** MRs ordered base target first, then mirrors; no inter-MR `Depends on`; each description has a `Hotfix mirror` section: `Mirrored to {mr_url:<repo>:<mirror>}` on the base MR, `Mirror of {mr_url:<repo>:<base>}` on mirrors (the orchestrator replaces them with `!N` after creating the MRs); one Jira comment lists all MRs.

## 10. Non-goals (v0.1)

Queue pulling from Jira boards, autonomy levels beyond `ask`/`draft-auto`, CI auto-fix without the orchestrator, non-Claude hosts.

## 11. Sessions and env lease

Batches (epics, review batches) can run each ticket in its **own visible host session**: the user opens, reads and steers each one, instead of watching a single orchestrator wait on hidden workers.

- **Workspace:**
  - `orchestration = {"sessions": true, "per": "ticket"|"run"}` (default off; `per` defaults to `ticket`, one session covering every run of that ticket);
  - `env = {"lease": true, "lease_ttl_s": 900}` (default off). Per repo `env` keys `slots`, `port_stride`, `shareable` and `login.handoff_rewrite` are validated by `workspace check` too.

  `workspace check` validates both blocks.
- **Parent session:**
  - does the batch intake and the single consolidated question round;
  - then, with `orchestration.sessions` and 2+ tickets, starts one session per ticket with the host's session tool, passing a brief with the run ids, worktrees, recorded user decisions and `/factory session <run-ids>`;
  - after that it only coordinates: `factory batch status <parent>` after each child report, the parent gate and report, and every dev.mcp write, only with the user's ok.

  Without a session tool (plain CLI) or when the host refuses, it falls back to worker subagents.
- **Child session:**
  - `factory run claim <run…>` records `{session, claimed_at, pid}` in `run.json.sessions` (the current owner is the last entry; the session id comes from `CLAUDE_CODE_SESSION_ID`, falling back to the other host hints);
  - commands that advance a run (`gate`, `prove`, `env up|login --run`) refuse when another live session owns it, unless `--takeover` (recorded as an event);
  - a process with no session id, such as a plain terminal, is not checked;
  - children never write the parent run or dev.mcp.
- **Run writes:**
  - `run.json` carries a `rev` counter;
  - `run_save` takes a per-run lock file (`run.json.lock`, `O_EXCL`), re-reads the disk copy and refuses with "changed on disk by another process" when `rev` moved since load, so a concurrent write fails loudly instead of being lost;
  - `run_update(run_id, fn)` (load, mutate, save under the lock) is used by the short mutators (`run human|block|unblock|decide|login-user|claim`);
  - `write_json` uses a unique temp name and retries `os.replace` on Windows sharing errors.
- **Env lease** (one lease per repo, so runs that touch different repos, or different slots of one repo, use the local env at the same time):
  - **State:** `env lease acquire|release|status <ws> --run <id> [--repo A ...] [--wait] [--timeout S]` keeps `FACTORY_HOME/env/<ws>/<alias>/lease.json` (slot 0) and `env/<ws>/<alias>@<k>/lease.json` (slot k > 0) under one `O_EXCL` lock file per workspace (`env.lock`). A slot file holds the holder run, session, pid, acquired_at and heartbeat; the slot-0 file also carries the repo's FIFO queue and its `shared` holders. A lease is stale when its heartbeat is older than `lease_ttl_s` (and its holder pid is not alive on this host) or its run is `done`/`blocked`; a stale lease can be reclaimed.
  - **Which repos:** without `--repo`, the runtime repos the run needs: its own repos that have an `env` block plus the `env.depends_on` closure (a run with none of them needs every repo with an `env`). Acquire is all-or-nothing, in repo `order`: a refused run holds nothing. Queued runs are served FIFO across repos by simulation under the lock: a queued run that can be given everything it asked for reserves it, one that cannot reserves nothing, so two queues can never deadlock each other. A waiter that stops polling for 120 s leaves the queue.
  - **Legacy lease:** a `env/<ws>/lease.json` held by a live run (not stale, run not finished) counts as holding every repo, every slot: other runs are refused until it is released or reclaimed, its holder is granted at once, and its heartbeat is kept by the same commands. `release` by the holder deletes it. For older factory versions, which only know that file, this version keeps a marker in it while any run holds a per-repo lease (slot or shared entry): `{"marker": "per-repo leases", "run": <one live holder>, "holders": [...], heartbeat, pid}`. `run` is a real holder (not the literal marker text) because an old version reclaims a lease whose run has no `run.json`; the marker moves to another holder when that one releases, its heartbeat is refreshed by every acquire/heartbeat, and it is removed when nothing is held. This version reads the marker as free: it never grants or blocks a repo, and a real legacy holder's file is never overwritten.
  - **Slots:** a repo `env.slots` (int, default 1) and `env.port_stride` (int, required when `slots` > 1; `workspace check` enforces it) let several runs run the same repo at once. In slot k every port of `ports`, and the port inside `health` and `base_url`, is the base port + k * stride. The start command gets the slot ports from the placeholders `{port}`, `{port0}`, `{port1}` (and `{slot}`) when any argument has one (also in `env_vars` values), otherwise literal occurrences of the base port numbers in the start arguments are replaced. The pid and log files, the login storage state (`<alias>@<k>[.<user-slug>].storage.json`) and the login block (`<alias>@<k>.login.json`) are keyed `<alias>@<k>`; slot 0 keeps today's names (a shared repo uses slot 0's). `env up` stores `env_digest` in the pid record: the sha256 of the resolved slot env (start args, `env_vars` after `{base_url:ALIAS}`/`{port:ALIAS}` and slot placeholders, `ports`). `binding_error` and `stale_reason` report a record whose digest differs from the run's current slot env (`serves another resolved env`, kind `stale`, so `prove` restarts it once when the run holds the lease); a record without `env_digest` is judged as before. Acquire takes the first free slot and the CLI records `env_slots: {alias: k}` in `run.json` (via `run_update`; release removes it). Everything that resolves a repo's env for a run uses that slot: the `base_url`/`health` a collector gets in `prove` (REPRO and BEFORE runs too), `env check|up|down|logs|login|seed|reset-data`, `binding_error`, `stale_reason`, `restart_*`. `env down|logs --slot K` addresses a slot without a run. `FACTORY_SLOT` is exported to the process when a repo configures slots.
  - **Cross-repo placeholders:** a repo's `env.env_vars` values and `env.start` arguments may contain `{base_url:<ALIAS>}` and `{port:<ALIAS>}` (the first port of `<ALIAS>`). They are resolved with the slot the run holds for `<ALIAS>` (`run.json` `env_slots`, slot 0 without one), so a React instance on slot 1 gets the `base_url` of the API instance on slot 1 (e.g. `"API_URL": "{base_url:API}/v1"`). `slot_env` resolves them after the slot's own placeholders; the referenced repo is read without its own references, so `A -> B -> A` cannot loop. `workspace check` fails on an alias that is not a repo of the workspace; at run time an unknown alias or a repo without a port is an error (in `prove`, any slot env that cannot be resolved records the check `error` with `details.fail_kind: setup` and `PROVE-FAIL ... kind=setup`; it never falls back to slot 0). `prove` baseline and quality commands get the resolved `env_vars` too.
  - **Shared repos:** a repo `env.shareable: true` is leased `shared` to a run with no worktree for it (the run does not change that repo): many shared holders at once, kept in slot 0's `shared` list. An exclusive acquire of slot 0 waits while shared holders exist, and a shared acquire waits while slot 0 is held exclusively or a queued exclusive run is waiting for the sharers to leave (no writer starvation); an exclusive run on another slot does not wait. A run that changes the repo always needs an exclusive slot. A shared holder never starts, stops or restarts the process: `env up` only probes it and, if it is not up, fails with `ENV-FAIL repo=<alias> kind=lease detail=shared repo <alias> not up; ask its holder or start it with env up`; `env down` and `--auto-restart` refuse; its binding check judges the recorded process only (it serves its holder's code, not this run's worktree). Runtime evidence records `details.shared = {alias: HEAD of the serving process's cwd}` for every shared repo the run needs, so a result can be traced to the other run's code it depended on: set `shareable` only on repos the team treats as stable. With `env.lease` off, `shareable` is inert.
  - **Enforcement:** with `env.lease`, `env up --run` (every repo it brings up, dependencies included), `env login --run` and `env seed|reset-data` require the run to hold the lease of that repo (exclusive slot, shared entry or legacy lease), and the read-record -> spawn -> pid-write sequence of `up` runs under the lock. `env down` refuses when another run holds the slot (or shares the repo, or the legacy lease is live) unless `--force`. `prove` and `env check` renew the heartbeat of every lease the run holds. `env lease release` stops the envs the run started in its slots (never a shared repo) unless `--keep-env`.
  - **Login across slots:** the session of the React app is a host-only cookie on `localhost` (the port does not matter) signed with the same secret in every instance, but the legacy login redirects to a fixed URL from its config (e.g. `http://localhost:3300/portal/coming?token=...`). A repo `env.login.handoff_rewrite: true` (needs a `success_url_contains` with `host:port`) makes `env login` for a slot k > 0 pass `handoff: {host, from_port, to_port}` to the browser CLI: a navigation answered on the slot's origin whose `Location` is that fixed origin, or any navigation to it, is moved to the slot's port (path, query and token kept), so the hand-off completes on the slot and the login succeeds on the slot's `base_url`. `success_url_contains` is slot-aware for every slot: the ports of the repo (and the hand-off port) found in it are shifted by k * stride. Slot 0 is unchanged. The storage state file is per repo, user and slot (see Slots).
  - **Without `env.lease`:** behaviour is unchanged (`env lease` still works when called; the slot keys apply to `env up --run` through `env_slots` only).
- **Visibility:**
  - `batch status <parent> [--json]` covers epic and review-batch parents. Per child it shows ticket, phase, next gate, open blockers, open `human` checks, owner session, the lease holders of the workspace, the env slots the child holds (`slots`, e.g. `API=1,React=0`) and its last prove. `epic status` uses the same rows.
  - `run log <run> [--tail N] [--since ISO] [--json]` prints `run.json` events as a timeline.
  - `run delete <run...> --yes [--force]` zips each run into `archive/runs/`, verifies the zip, then removes the folder. Without `--force` only `done`, `report` or `blocked` runs are deleted. A parent must be deleted together with its children. A run claimed by another session is refused. Worktrees are listed, never removed. The command is reserved for the main session.
  - `metrics` attributes child-session transcripts (marker `factory-run: <child>`) to the parent too.
- **Exploration is not proof.** In the UI phase a child may drive the host's built-in browser against the local env and the Figma frames, to find gaps and write Playwright specs with real selectors. Only collectors write evidence; nothing seen in that browser is a PASS.

## 12. Visual evidence on request

Screenshots of a change are something the user may want to see, and the factory used to take them only when asked at ship (outside `prove`, with no before image). Now the user is asked once, and a yes is enforced by gates.

- **UI run.** A ticket run touches UI when a touched repo is a UI repo (workspace repo `ui: true`; when `ui` is unset, a repo whose `env` has a browser `login` block, else a repo whose diff vs its merge-base contains `*.tsx`, `*.jsx`, `*.vue`, `*.svelte`, `*.css`, `*.scss`, `*.less`, `*.html`, `*.cshtml`, `*.aspx` or `*.razor` files), an AC is `kind: ui`, or `acs.json` has `browser`/`visual`/`style`/`screenshot` checks. `ui: false` opts a repo out. "Touched" means the repo has changes vs its merge-base; while nothing is changed yet (plan time) every branched repo counts. The diff is re-evaluated at `gate prove`, so a UI change discovered later still demands the answer. Set `ui` explicitly on every repo with an `env` block: `workspace check` warns when it is missing (not a failure) and rejects a non-boolean value. A `screenshot` check may not carry `before` (the factory sets it itself on the base capture). Review, epic-parent and batch runs are not asked.
- **The question.** For a UI run, `gate plan` fails until a user decision carries `visual: yes|no`: `factory run decide <run> "<answer>" --by user --user-said "<gist>" --visual yes|no`. The latest such decision wins. The skill asks in the single question round: for a bug, before/after screenshots of the fix (merge-base vs fixed HEAD, same steps); for a feature, screenshots of the implemented screens. The default is yes.
- **`screenshot` check** (author-written): `{"id", "type": "screenshot", "repo", "title"?, "path" | "spec", "viewport"?, "wait_for"?, "selector"?, "settle_ms"?}`. It has exactly one of `path` (one capture of the page) or `spec` (a Playwright spec with the steps that reach the state, run with `--screenshot on`: each test ends with a screenshot, and `page.screenshot({path: testInfo.outputPath(...)})` adds named ones). It is a runtime check: it needs the repo env and env binding like `browser`. It must be referenced by an AC like every check. It is documentation, not an assertion: it never counts as a reproduction or as a `bug`/`ui` AC's proof, and `--repro` never treats it as a REPRO check.
- **With `visual: yes`:**
  - `gate plan` needs ≥1 `screenshot` check per touched UI repo (≥1 overall when the run has no UI repo).
  - Feature runs: the after image is the check's normal evidence at HEAD, so the prove gate requires it like any check.
  - Bug runs: `factory prove <run> --repro --assume-env` also runs every `screenshot` check against the env serving the clean run worktree at the merge-base. Like runtime repro checks, it runs before any fix commit, and the same env-binding rule applies. It writes `evidence/BEFORE-<id>.json` (`kind: before`, `git_sha` = merge-base; `pass` = ≥1 listed PNG that exists on disk, and a failed step on the unfixed base is tolerated). `gate reproduce` and `gate prove` require a `BEFORE-<id>` with status `pass`, a matching digest event, and `git_sha` equal to the current merge-base. Hotfix runs capture it on the base target only.
  - A yes recorded after the plan lock, with no screenshot checks yet, fails `gate prove` with the replan command (`run replan … --decision <n>`).
  - Because `proof_errors` re-runs the prove criteria, the review gate, `ship plan`, `ship verify` and `gate ship` re-check all of this.
- **Ship.** `ship-plan.json` carries `visual_evidence: [{check, repo, acs, screen, before[], after[], before_sha, after_sha, files[]}]`: run-relative artifacts plus absolute `files` for the briefing. The epic ship plan concatenates the children's, with `child`. Each MR description gets a `## Visual evidence` table (check, ACs, screen, before and after file names). At Gate S the orchestrator sends the `files` to the user next to the briefing. dev.mcp has no GitLab upload tool, so the images are not attached to the MR: the table names them, and the files stay in the run's `evidence/`.
- **With `visual: no`:** nothing changes. Browser/visual/style evidence is still required as before.

## 13. Fail fast and recovery

Real runs lost most of their time to slow failing checks, misleading env diagnostics and workers retrying after the first infra failure. These rules make a blocking condition surface in minutes.

- **Per-check cap.** Every runtime check has a wall-clock cap: the check's `timeout_s`, else `limits.check_timeout_s`, else 120 s for browser, visual, style and screenshot, or 60 s for api. When it hits the cap the process tree is killed. Playwright gets a per-test timeout below the cap and a 30 s navigation timeout (`--goto-timeout-ms`, `--wait-until load` unless the check sets `wait_until`). `test` checks keep their own timeout.
- **Env failures stop the batch.** An env-kind failure marks the remaining runtime checks of that repo `skipped: env`, and `prove` exits 3. Env-kind failures are connection refused, a 5xx health, a login failure, or a timeout on a repo's first runtime check. Two consecutive identical failures (same kind, same first line) stop the runtime batch.
- **Machine-readable lines.** `prove` and `env` print `PROVE-FAIL check=<id> kind=<timeout|assert|flaky|env|setup> detail=…` and `ENV-FAIL repo=<alias> kind=<unhealthy|stale|port|lease|start|timeout|usage|seed|preflight> detail=…`. With `--json` they go to stderr. `prove` exits 0 on pass, 1 on a check failure, 2 on usage and 3 on an env failure.
- **Preflight.** `factory env check <ws> [repo] [--run R] [--auto-restart]` infers repo and run from a run-worktree cwd. Healthy means a status below 500, and redirects are not followed. Exit codes: 0 healthy, 1 unhealthy, 2 usage or capability, 3 stale (the process is not at the worktree HEAD), 4 port or lease conflict. The orchestrator runs it before delegating any runtime-dependent worker and passes the result in the request (`env_preflight`).
- **Stale env.** `prove` restarts a stale env once (down, then up) when the run holds the lease.
- **Process safety.** Factory only stops processes it started. The pid record's create time must match the live process (a record without it is never killed). Factory never stops itself or its ancestors. A record that does not match is treated as foreign and is reported, never killed. A port held by HTTP.sys (PID 4, IIS Express) is judged by its health after three probes.
- **Lease.** The heartbeat is renewed before every check. A holder whose pid is alive on the same host (create time checked) keeps the lease past `lease_ttl_s`. `env lease release` stops the run's own envs unless `--keep-env`.
- **Worker contract.** After the first infra signal (an `ENV-FAIL` line, `prove` exit 3, a non-zero `env check` or `env up`, a missing tool or SDK), a worker may make one documented self-repair (`env check --auto-restart`). Then it hands back `status: blocked` with `infra_signal`, `first_seen_at` and `tried`. The `failfast.js` hook is wired into author, builder and auditor on PreToolUse, PostToolUse and PostToolUseFailure. It counts same-kind infra failures per agent. On the second one it tells the worker to hand back now, and it then denies further `factory env up|check|prove`. A healthy check or a passing prove resets the count. On any error the hook fails open.
- **Waiting.** Workers cannot `sleep`. `factory wait --file P [--contains T] | --cmd C --until-exit N | --url U [--status 2xx|3xx|200] [--timeout S] [--poll S]` prints `WAIT-OK` or `WAIT-TIMEOUT` and exits 0 or 1.
- **Guards.** Read-only shell commands and scratch scripts that only read run files are allowed. Writes to CLI-owned run files stay denied. `runs/_inbox/**` is writable by every role, scouts included.
- **Proof at plan.** When the env is up, the author dry-runs each new browser or api check (`factory prove <run> --check CHK-n`) before `gate plan`, so a bad selector or an unexpected redirect costs a minute, not a replan.
- **Recovering runs.**
  - `factory run verify-human <run> CHK-n --note … --by user --user-said …` records a human check the user confirmed. A qa `CHANGES` caused only by pending human checks is reported as pending and counts no review loop.
  - A replan that changes only checks keeps the `code` review.
  - `review fix` records the MR head, and `gate build` checks only the commits after it (`--no-merges`). Commits inherited from the run's targets, dependency branches or open MR source branches are skipped.
  - `run close <run> --reason` puts a run in the terminal `closed` phase, which can be deleted without `--force`. `run list` hides closed runs and `--all` shows them.
  - `run retype --bug|--feature|--hotfix` changes the run type before `gate build`. `run start` derives a bug from the Jira issuetype.
  - Blocker kind `decision`. `workspace list|show` redacts secrets.
- **Collectors.** dotnet and VS output is forced to English (`DOTNET_CLI_UI_LANGUAGE=en`, `VSLANG=1033`; user values win). A test or red-green check that runs zero tests ("No test matches", "No tests found", "collected 0 items" and the like) fails as `setup` ("no tests matched"). Files generated under `checks/` (`out`, `screenshots`, `test-results`…) are excluded from the plan lock, and `adapter`/map files are locked wherever they sit in the run dir.
- **Ship.** The MR title defaults to `[{key}] - {summary}` (`ship.title_format`). The description has an AC × check × status table with `<details>` of the key output lines, and never a local file link: `ship verify` fails on `](evidence/`, `](C:`, `](./` and `file://`. Reviewers need `gitlab_username`. `ship plan --jira none|comment|transition` (default `ship.jira`, else both). `ship update-description` rebuilds the description from the current evidence. The `## Quality` section lists failing baseline tests, per target on a hotfix.

## 14. Fast verification

A 54-check run spent 21.8 h in `prove`: passing checks were re-run 15-20 times at the same sha, a new check ran last and failed after 27 min, and a hot-reloading dev server was restarted on every HEAD. `prove` now fails fast and passes fast.

- **Risk order.** Before running, `prove` orders the AC checks: (a) last evidence `fail`/`error`, (b) no evidence or a changed check digest, (c) its repo has commits since the evidence sha, (d) the rest. Inside a group the cheapest type first (`test`, `red-green`, `api`, `style`, `visual`, `screenshot`, `browser`), ties by the last evidence `duration_s`, then plan order. Quality and rules still run after the AC checks.
- **Check digest.** `integrity.check_digest` is the sha256 of the check entry (without `id`) plus the bytes of the run-dir files it reads (`spec`, `adapter`, `map`, `script`, `cmd` paths). Every evidence record carries it in `details.check_digest` (quality: its commands + baseline merge-base).
- **Reuse.** A check whose latest evidence is `pass`, at the repo's current HEAD, not dirty, with the same `check_digest` and still valid for the gates (event digest, plan lock) is not run again. A runtime check (`browser|visual|style|api|screenshot`) also exercises the other repos, so its evidence records `details.run_heads = {alias: HEAD}` of every repo of the run and is reused only when all of them are unchanged (missing `run_heads` = not reusable); `integrity.evidence_error` likewise treats runtime evidence whose recorded `run_heads` differ from the current ones as stale (evidence without `run_heads` is judged as before), and any evidence whose `details.check_digest` differs from the current digest of its check (its `acs.json` entry or a file it reads changed, whatever path relocked the plan): evidence without `check_digest` is judged as before. `--fast` evidence is reused only by another `--fast` run. Reuse is computed once per check per `prove` invocation: `REUSED CHK-n`, and the evidence file and event stay as they are. `--all` runs everything. Gates read reused evidence exactly as before: it is the same record.
- **`--bail`.** The first runtime check classified `assert` stops the runtime batch: the remaining runtime checks are recorded `skipped: bail (not run: <check> failed: <detail>)` (same path as the env and repeat stops) and `prove` exits 1.
- **Modes.** `--fast` = bail + reuse. `--final` = every check, no reuse, no bail. Neither = reuse only. Each record carries `details.mode` (`fast|final|default`); each `prove` run appends a `prove` event `{mode, ran, reused, skipped, failed, wall_s, bail}` to `run.json`. `--fast` and `--final` are exclusive.
- **Gate rule.** `gate prove` (and everything that re-runs the prove criteria) refuses a check whose latest evidence has `details.mode == "fast"` or `details.hot_reload == true` and names `factory prove <run> --final`. Other `default` and `final` evidence is accepted.
- **Hot reload.** A repo `env.hot_reload: true` (boolean, validated by `workspace check`) means the server follows commits in its worktree: in the default and `--fast` modes a HEAD that differs from the one recorded at `env up` is neither stale (`stale_reason`, `binding_error`) nor refused by `env up`, and runtime evidence collected that way records `details.hot_reload: true`, which `gate prove` refuses like fast evidence (nothing proves the server actually reloaded). `prove --final` treats a hot_reload repo like any other: a HEAD mismatch is stale, so the env is restarted once (lease held) or the check fails `stale`, and final evidence always comes from a process started at HEAD. A different cwd or resolved env is stale in every mode. Evidence still records the current HEAD.
- **`run amend-check`.** After the plan lock, the author edits the check, then `factory run amend-check <run> CHK-n --kind timing|selector --reason …`. The plan lock keeps each check entry and a digest of `acs.json` without `checks`; the command refuses unless the diff against it is limited to `timeout_s`, `wait_for`, `wait_until`, `expect_timeout_ms` of that check (selector also allows changes in the spec files of that check under `checks/`, unless another check reads the same file: the command lists those files and checks and points at `run replan`). It is refused while `workspace.json` differs from the plan lock (`workspace changed since plan lock: replan`), and the relock carries the locked workspace digest and autonomy caps instead of re-reading them. Anything else lists the offending fields and points at `run replan`. On success the plan is relocked keeping `seq` (other evidence stays valid; the amended check's older evidence is refused by `evidence_error` until it is re-proven), an `amend_check` event is recorded and the phase does not move. It counts like a replan against `autonomy.max_replans` (`--by user` is the approved path), except `--kind timing` when the workspace sets `autonomy.allow_timing_amends: true` (boolean, validated by `workspace check`).
- **Scoped quality.** A repo may add `quality_fast` (same shape as `quality`: name -> command; validated by `workspace check`). Only in `--fast` mode `prove` runs it instead of `quality`; a command may contain `{changed}`, replaced by the quoted, space-separated files of `git diff --name-only <merge-base>...HEAD` (merge-base from the baseline) that still exist. No changed file: the command is skipped as a pass (`<name>: no changed files`). The baseline and the default/final modes keep the full `quality`; fast evidence is refused by `gate prove`, so the `--final` run is always the full one. The quality digest includes `quality_fast` in fast mode, so fast and full evidence are never swapped.
- **Flaky.** A `browser` check that fails with an assert (not env, timeout or setup) is re-run once at the same sha. If the retry passes, the evidence stays `fail` with `details.flaky = true`, summary `FLAKY: ...` and `prove` prints `PROVE-FAIL check=<id> kind=flaky`; flaky is never a pass. If it fails again it is a normal fail. `--no-retry` disables the retry.
- **Batched browser checks.** Each `run-spec` boots Playwright and loads the login state again (20-40 s of overhead, ~30 browser checks per run). When two or more `browser` checks of the same repo and target are about to run (not reused, not skipped), `prove` runs them in ONE Playwright process: `browser/dist/cli.js run-specs --manifest ... --base-url ... [--storage-state ...] [--max-failures 1]` (one worker, one Playwright project per check with its own per-test timeout and output dir, the env login's `storageState` shared, json reporter). The batch starts where its first check sits in the risk order and keeps that order; later members take their result from it. Results are split into the same evidence records as before (same fields, artifacts `evidence/<id>/report.json|run.log` per check, `duration_s` from the reporter per check, same `collector` string) with `details.batched: true`. Preserved: the per-check caps (the process cap is their sum, `--timeout-ms` below it), fail-fast (`--bail`/`--fast` pass `--max-failures 1`; unrun checks become `skipped: bail`; env and repeat stops mark the rest `skipped` exactly as when run one by one, even if Playwright already ran them), env-kind classification, the flaky retry (only the failed checks, one by one, outside the batch), `--no-retry`. A check Playwright did not reach (global timeout) and nothing explains is run alone. A check with an unusable spec/base_url/login gets its own error and leaves the batch; with fewer than two usable specs, a stale env binding, a crash, a timeout without `batch.json` or a report that cannot be mapped, `prove` logs `batch: ... running them one by one` and runs the checks individually. Opt-out: workspace `limits.browser_batch: false`.
- **`prove --estimate`.** Runs nothing and writes nothing (no lease heartbeat, no env restart, no data reset). Prints, per check in the order `prove` would use, `REUSED` (0 s) or `RUN` with its expected seconds: the last `duration_s` of its evidence, else the default of its type (test 10, api 15, style/visual 25, screenshot 30, browser 60, quality = last, 30 before any). Totals: for the chosen mode, `--fast` (reuse passing evidence) and `--final` (everything runs). `--json` prints `{run, mode, checks: [{check_id, type, action, expected_s, last_s}], total_s, fast_s, final_s}`. It ignores batching (an upper bound for browser checks). The orchestrator uses it to answer "how long will this take".
- **Deterministic test data.** `env.seed` (`null` or `{"cmd": [...], "cwd": "...", "reset": [...]}`, argv arrays, `cwd` relative to the run worktree) runs with `FACTORY_RUN`, `FACTORY_TICKET` and `FACTORY_DATA_PREFIX` (`UAT<ticket digits>`, e.g. `UAT9451`) set. `factory env seed <ws> <repo> --run R` runs `cmd`; `factory env reset-data <ws> <repo> --run R` runs `reset` (idempotent cleanup by prefix plus restoring the seed is the script's job). Each records an `env_seed` / `env_reset` event with the exit code; a non-zero exit prints `ENV-FAIL repo=<alias> kind=seed`. `prove` (not `--check` runs) calls the reset once per runtime repo that declares `seed.reset` and still has a runtime check to run, before the runtime batch; a failure is an env failure (exit 3, the repo's runtime checks are skipped).
- **Env preflight.** `env.preflight: [{"name": "...", "cmd": [...]}]` commands run in the repo worktree at the end of a healthy `factory env check`; a non-zero exit makes the check exit 1 with `ENV-FAIL repo=<alias> kind=preflight detail=<name>` (e.g. a daily DB dump reset dropped a trigger).
