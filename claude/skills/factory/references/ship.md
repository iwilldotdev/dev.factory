# Ship how-to (main session only)

`R` = `FACTORY_HOME/runs/<run-id>`. Phase is `ship` after `gate review` passes. Ship is provider-neutral: `ship-plan.json` lists **intents**; you execute each with whatever tool the SCM and tracker offer (an MCP server or a CLI), then read the result back as a raw payload and ingest it. The SCM and tracker profiles' hints (`FETCH` lines) say how to read back.

1. `git -C <worktree> fetch origin` for every repo of the run.
2. `factory ship plan <run>`. It fails when a branch is behind `origin/<target>`, a dependency change is not merged (read from its change contract), a plan file changed, or the worktree moved after prove (commit, dirty file). Behind: a builder rebases/merges, then `factory run rewind <run> prove "<reason>"` and run prove → review → ship again; or ask the user (`--allow-behind` only with their explicit yes). Never commit, rebase or merge at ship without rewinding: `ship plan`, `ship verify` and `gate ship` re-check the proof against the current HEAD. A plan file of an older schema is refused ("re-run ship plan").
2b. Ticket handling is chosen at plan: `factory ship plan <run> --ticket none|comment|transition` (`none` = no ticket action, `comment` = comment only, `transition` = transition only; the default is the workspace `ship.ticket_mode`: `none|comment|transition|comment+transition`, else `comment+transition`). The comment is planned when `ship.ticket_comment` is `"change-links"`, the transition when `ship.ticket_transition` (or the epic's) names a status. Ask in the Gate S briefing when the ticket's workflow makes a transition unsafe. Titles are `[KEY] - summary` (workspace `ship.title_format`): use the plan's `title` verbatim; it never carries a draft marker, `draft` is its own field.
3. Read `R/ship-plan.json` (`schemaVersion: 2`): `changes[]` (repo, target, `source_branch`, `target_branch`, `head_sha` = the proven commit, `title`, `draft`, `body_md`, `depends_on`, `reviewers`, `readback` path) and `actions[]` in order, each with `needs_user`. Bodies are Markdown; link placeholders `{change_url:<repo>:<target>}` (epic: `{change_url:<child>:<repo>:<target>}`) are replaced by the change URL from the readback contracts of earlier changes.
4. **Gate S** for every action with `needs_user: true`: one chat briefing listing the changes (repo → target, draft, title, Depends on), ACs × evidence status, `human` checks, `approx` design frames, the ticket comment and the transition. When `visual_evidence` is not empty, send its `files` (before, then after, per check) to the user with `SendUserFile` in the same turn; each description already has a `## Visual evidence` table naming them. Wait for an explicit yes. The approval covers only the listed actions.
5. Execute the intents in order. Always from the plan's values, never from memory:
   - `push`: `git -C <worktree> push -u origin <branch>`. Never force. The pushed tip must be the plan's `head_sha`.
   - `change_request` (`op: create|update`, `number` when updating): create or update the change request with `title`, `body_md` (converted to the SCM's format), `draft`, `source`/`target_branch`, `reviewers`. Set the draft flag with the SCM's own mechanism; do not rely on a title prefix.
   - `set_draft`: flip the draft state of the existing change to the plan's `draft`.
   - `readback`: read the change back and save the raw payload at the action's `save_to` (`R/raw/change/<repo>-<target>.<ext>`), then run the action's `ingest` line (`factory ingest <run> change <raw> --id <repo>-<target> --repo <alias>`). Never paste or rewrite the payload.
   - `pipeline_watch`: save the pipeline payload at `save_to` and its jobs payload at `jobs_save_to`, then the action's `ingest` line (`--raw jobs=<path>`). A running pipeline is reported, not judged.
   - `issue_comment`: post `body_md` (converted) on each issue in `issues`. If the epic has a `ship_comment` template, use that instead.
   - `issue_transition`: move each issue to `to_status` through the tracker's allowed transitions.
6. `factory ship verify <run>` compares each change contract with the plan (repo, source and target branch, title, `draft`, reviewers, and the change `head_sha` against the proven `head_sha`) and the pipeline contract's `sha` for watched changes; for a missing or stale readback it prints the `FETCH` line. Fix title/draft mismatches with another `change_request`/`set_draft` and readback; a head mismatch means unproven commits are on the branch: rewind to prove.
7. `factory gate <run> ship`. Then go to feedback. After a late edit of evidence, `factory ship update-description <run> [--repo R --target T]` rebuilds the change bodies and their `change_request` update intents.

A run that will not ship: `factory run close <run> --reason "<why>"` (releases lease and env).

Never un-draft, merge, or close a change request without an explicit user request for that change.

## Hotfix runs

**Mirror = same diff.** The mirror branch carries the same changes as the base fix; commits and branches may differ, the changes may not. On a `run mirror` conflict the builder reproduces the base diff and adapts only what the mirror branch structurally requires (a moved file, an import path). No reformatting, no relocating tests, and the formatter only in check mode, never write mode on a whole file. Then run `factory run mirror-diff <run>` (read-only, `--json`; exit 1 and the divergent files and hunks when the mirror differs). `gate prove` (and `gate build` after a rewind) and `ship plan` fail on any divergence: other lines, the same lines in another function (git function context; neighbouring lines and imports of a moved module are not compared) or other line endings; the output names the refs and merge-bases compared (fetch first when it hints that local and origin target refs differ). The only exception is the user's own decision: `factory run decide <run> "mirror diff: <reason>" --by user --user-said "<quote>"`, then `--allow-mirror-divergence <n>` on `gate prove`, `gate build` or `ship plan` (stored on the run, valid only for that exact divergence: any change to it invalidates the allowance); the reason and the divergent files go into the mirror change description.

`ship plan` orders changes base target first, then mirrors. Descriptions end with `Mirrored to {change_url:<repo>:<mirror>}` (base change) and `Mirror of {change_url:<repo>:<base>}` (mirror change): after creating both, replace the placeholders with the real links in the descriptions (update the first change once the second exists). One ticket comment lists both. Push and create the base change first. Runtime checks on a mirror: `factory env down <ws> <repo> --run <run> --target <current target>` (also stops the deps this run started for it; an env another run or a manual `env up` started is never stopped or restarted) then `factory env up <ws> <repo> --run <run> --target <mirror>` and `factory prove <run> --target <mirror> --final`; prove the base target the same way. `prove --target` and `env check --auto-restart --target` switch targets by themselves only for envs this run started (dependencies restart first); any other env is reported as `env serves ... (run <id>|none)` and left alone.

Repos marked `env_only` in run.json (`run branch --env-only`, `run env-only`) only served the env: `ship plan` lists no push, change request or readback for them, and you do not fetch or push them.

A repo may map a logical target to another branch (`target_branches` in its workspace entry, e.g. `{"<target>": "<other branch>"}` in one repo while another keeps the target name). The plan keeps the logical target for ordering and names, but each change's `target_branch` is the repo's mapped branch (read it from `ship-plan.json`, never assume the target name), and `ship verify` compares the readback against it. `run mirror` for that repo branches from the mapped branch.
