# Ship how-to (main session only)

`R` = `FACTORY_HOME/runs/<run-id>`. Phase is `ship` after `gate review` passes.

1. `git -C <worktree> fetch origin` for every repo of the run.
2. `factory ship plan <run>`. It fails when a branch is behind `origin/<target>`, a dependency MR is not merged (from `R/remote/`), a plan file changed, or the worktree moved after prove (commit, dirty file). Behind: a builder rebases/merges, then `factory run rewind <run> prove "<reason>"` and run prove → review → ship again; or ask the user (`--allow-behind` only with their explicit yes). Never commit, rebase or merge at ship without rewinding: `ship plan`, `ship verify` and `gate ship` re-check the proof against the current HEAD.
2b. Jira handling is chosen at plan: `factory ship plan <run> --jira none|comment|transition` (`none` = no Jira action, `comment` = comment only, `transition` = comment and transition). Default `comment`; ask in the Gate S briefing when the ticket's workflow makes a transition unsafe. MR titles are `[KEY] - summary`: use the plan's `title` verbatim.
3. Read `R/ship-plan.json`: `mrs[]` (repo, target, source/target branch, `head_sha` = the proven commit, title, draft, description, `depends_on`, readback path), `jira_comment` (ADF), and `actions[]` in order, each with `needs_user`.
4. **Gate S** for every action with `needs_user: true`: one chat briefing listing the MRs (repo → target, draft, title, Depends on), ACs × evidence status, `human` checks, the Jira comment and the transition. When `visual_evidence` is not empty, send its `files` (before, then after, per check) to the user with `SendUserFile` in the same turn; each MR description already has a `## Visual evidence` table naming them. Wait for an explicit yes. The approval covers only the listed actions.
5. Execute the actions in order:
   - `push`: `git -C <worktree> push -u origin <branch>`. Never force. The pushed tip must be the plan's `head_sha`.
   - `mr`: `gitlab_save_merge_request` (create, or update when an MR already exists for the source → target) with title, description, `draft`, source/target branch, assignee/reviewer from the workspace. Keep the `Draft: ` title prefix when draft: the MCP may ignore the flag. Stacked MRs: fill `Depends on !N` from the readbacks of earlier MRs in the plan.
   - `readback`: `gitlab_get_merge_request` with `save_to=<the action's save_to made absolute: R/remote/mr-<repo>-<target>.json>` and `overwrite: true`. The saved file wraps the MR as `{merge_request: {...}}`; `ship verify` reads both shapes. Never paste or rewrite it.
   - `jira_comment`: `jira_add_comment` with the plan's ADF on each issue. Replace `{mr_url:<repo>:<target>}` with `web_url` from the readbacks. If the epic has a `ship_comment` template, use that instead.
   - `jira_transition`: `jira_get_transitions`, then `jira_transition_issue` to the named transition.
6. `factory ship verify <run>` compares the readbacks with the plan, including the MR head `sha` against the proven `head_sha`; for a missing readback it prints the call (`FETCH gitlab_get_merge_request ... save_to=... overwrite=true`). Fix title/draft mismatches with another `gitlab_save_merge_request` and readback; a head mismatch means unproven commits are on the branch: rewind to prove.
7. `factory gate <run> ship`. Then go to feedback.

A run that will not ship: `factory run close <run> --reason "<why>"` (releases lease and env).

Never un-draft, merge, or close an MR without an explicit user request for that MR.

## Hotfix runs

**Mirror = same diff.** The mirror branch carries the same changes as the base fix; commits and branches may differ, the changes may not. On a `run mirror` conflict the builder reproduces the base diff and adapts only what the mirror branch structurally requires (a moved file, an import path). No reformatting, no relocating tests, and the formatter only in check mode, never write mode on a whole file. Then run `factory run mirror-diff <run>` (read-only, `--json`; exit 1 and the divergent files and hunks when the mirror differs). `gate prove` (and `gate build` after a rewind) and `ship plan` fail on any divergence: other lines, the same lines in another function (git function context; neighbouring lines and imports of a moved module are not compared) or other line endings; the output names the refs and merge-bases compared (fetch first when it hints that local and origin target refs differ). The only exception is the user's own decision: `factory run decide <run> "mirror diff: <reason>" --by user --user-said "<quote>"`, then `--allow-mirror-divergence <n>` on `gate prove`, `gate build` or `ship plan` (stored on the run, valid only for that exact divergence: any change to it invalidates the allowance); the reason and the divergent files go into the mirror MR description.

`ship plan` orders MRs base target first (homolog), then mirrors (pack). Descriptions end with `Mirrored to {mr_url:<repo>:<mirror>}` (base MR) and `Mirror of {mr_url:<repo>:<base>}` (mirror MR): after creating both MRs, replace the placeholders with `!N`/URLs in the descriptions (update the first MR once the second exists). Post one Jira comment listing both MRs. Push and create the base MR first. Runtime checks on a mirror: `factory env down <ws> <repo> --run <run> --target <current target>` (also stops the deps this run started for it; an env another run or a manual `env up` started is never stopped or restarted) then `factory env up <ws> <repo> --run <run> --target <mirror>` and `factory prove <run> --target <mirror> --final`; prove the base target the same way. `prove --target` and `env check --auto-restart --target` switch targets by themselves only for envs this run started (dependencies restart first); any other env is reported as `env serves ... (run <id>|none)` and left alone.

Repos marked `env_only` in run.json (`run branch --env-only`, `run env-only`) only served the env: `ship plan` lists no push, MR or readback for them, and you do not fetch or push them.

A repo may map a logical target to another branch (`target_branches` in its workspace entry, e.g. `{"pack": "dev"}` in the API while React keeps `pack`). The plan keeps the logical target for ordering and names, but each MR's `target_branch` is the repo's mapped branch (read it from `ship-plan.json`, never assume the target name), and `ship verify` compares the readback against it. `run mirror` for that repo branches from the mapped branch.
